# 예외 설계 — 장인몰 (미담)

## 1. 예외 계층도

```
RuntimeException
  └── BusinessException                     # global/exception/BusinessException.java
        ├── NotFoundException               → ErrorCode.NOT_FOUND (404)
        ├── ConflictException               → ErrorCode.CONFLICT (409)
        ├── ConcurrentUpdateException       → ErrorCode.CONCURRENT_UPDATE (409)
        ├── ForbiddenException              → ErrorCode.FORBIDDEN (403)
        └── BusinessRuleViolationException  → ErrorCode.BUSINESS_RULE_VIOLATION (422)
```

도메인 계층은 `BusinessException` 서브클래스만 throw한다.
Spring Security 필터 예외(`AuthenticationException`, `AccessDeniedException`)는 `SecurityConfig`의 `AuthenticationEntryPoint` / `AccessDeniedHandler`로 처리한다.

## 4. 계층별 예외 사용 규칙

### 4-1. API 계층 (Presentation)

| 상황 | 처리 방식 |
|---|---|
| 요청 파라미터/바디 유효성 오류 | `@Valid` → `MethodArgumentNotValidException` → `GlobalExceptionHandler` 자동 처리 |
| 경로 파라미터 타입 오류 (숫자 자리에 문자) | `MethodArgumentTypeMismatchException` → `GlobalExceptionHandler` 자동 처리 |
| JSON 파싱 실패 | `HttpMessageNotReadableException` → `GlobalExceptionHandler` 자동 처리 |

컨트롤러에서 직접 예외를 throw하지 않는다. 1차 검증은 `@Valid`에 위임한다.

```java
// 올바른 예
@PostMapping("/products")
public ResponseEntity<ProductResponse> create(@RequestBody @Valid ProductCreateRequest request) {
    return ResponseEntity.status(201).body(productService.create(request));
}
```

### 4-2. 비즈니스 계층 (Application / Domain)

비즈니스 규칙 검증은 Service 또는 Domain 객체에서 수행하고 `BusinessException` 서브클래스를 throw한다.

```java
// 올바른 예
public void cancel(Long orderId, Long memberId) {
    Order order = orderRepository.findById(orderId)
        .orElseThrow(NotFoundException::new);

    if (!order.isOwnedBy(memberId)) {
        throw new ForbiddenException("본인 주문만 취소할 수 있습니다");
    }

    if (!order.isCancellable()) {
        throw new BusinessRuleViolationException("배송 완료 후에는 취소할 수 없습니다");
    }
}
```

**null 사용 금지**: 존재하지 않는 리소스는 `Optional.orElseThrow(NotFoundException::new)`로 처리한다. null 반환 또는 null 체크 로직 작성은 엄격히 금지한다.

### 4-3. DB / JPA / Infrastructure 계층

| 상황 | 예외 | 매핑 |
|---|---|---|
| UNIQUE 제약 위반 | `DataIntegrityViolationException` | `ErrorCode.CONFLICT` |
| 낙관적 락 충돌 (`@Version`) | `ObjectOptimisticLockingFailureException` | `ErrorCode.CONCURRENT_UPDATE` |
| 비관적 락 타임아웃 | `CannotAcquireLockException` (필요 시 별도 핸들러 추가) | `ErrorCode.CONCURRENT_UPDATE` |

Infrastructure 계층은 JPA/DB 예외를 직접 처리하지 않고 `GlobalExceptionHandler`까지 전파한다.
단, 원인이 명확한 경우 (예: 특정 UNIQUE 제약 위반을 비즈니스 의미로 변환해야 할 때) Service에서 catch 후 `ConflictException`으로 재throw할 수 있다.

```java
// 필요한 경우에만 — 기본은 전파
try {
    wishlistRepository.save(wishlist);
} catch (DataIntegrityViolationException ex) {
    throw new ConflictException("이미 찜한 상품입니다");
}
```

### 4-4. Entity 설계 규칙

Entity에서 상태 전이를 검증할 때 도메인 예외를 throw한다.

```java
// 콘텐츠 Entity 예시
public void approve() {
    if (this.status != ContentStatus.PENDING_REVIEW) {
        throw new BusinessRuleViolationException("검토 대기 상태에서만 승인할 수 있습니다");
    }
    this.status = ContentStatus.APPROVED;
    this.version++;
}
```

Entity 메서드에서는 `BusinessRuleViolationException` 또는 `ConflictException`만 사용한다.
`ForbiddenException`, `NotFoundException`은 Service 계층의 권한/존재 검사에서만 사용한다.

## 5. GlobalExceptionHandler 매핑 요약

| 예외 클래스 | ErrorCode | 로그 레벨 |
|---|---|---|
| `MethodArgumentNotValidException` | `INVALID_INPUT` | WARN |
| `BindException` | `INVALID_INPUT` | WARN |
| `MethodArgumentTypeMismatchException` | `INVALID_INPUT` | WARN |
| `HttpMessageNotReadableException` | `REQUEST_BODY_MALFORMED` | WARN |
| `DataIntegrityViolationException` | `CONFLICT` | WARN |
| `ObjectOptimisticLockingFailureException` | `CONCURRENT_UPDATE` | WARN |
| `BusinessException` (및 서브클래스) | `errorCode()` 위임 | WARN |
| `Exception` (catch-all) | `INTERNAL_ERROR` | ERROR + stack trace |

Security 필터 예외는 `GlobalExceptionHandler`를 거치지 않는다. `SecurityConfig` 내 핸들러에서 직접 `ApiErrorResponse`를 직렬화해 응답한다.

## 6. ResponseBodyAdvice — 자동 래핑 규칙

`GlobalResponseAdvice`가 `@RestController` 응답을 자동으로 `ApiResponse<T>` 봉투에 래핑한다.

| 조건 | 동작 |
|---|---|
| 이미 `ApiResponse<?>` 또는 `ApiErrorResponse` | pass-through (double-wrap 방지) |
| `text/event-stream` (SSE) | pass-through |
| `StringHttpMessageConverter` 사용 | pass-through (ClassCastException 방지) |
| `ByteArrayHttpMessageConverter` 사용 | pass-through |
| body == null (204) | null 반환 |
| 그 외 모든 DTO | `ApiResponse<T>` 래핑, status는 실제 HTTP 상태코드 반영 |

컨트롤러는 `DTO` 또는 `ResponseEntity<DTO>`를 반환하면 된다. `ApiResponse.ok(dto)` 직접 반환도 허용하지만 `GlobalResponseAdvice`가 중복 래핑을 방지한다.

## 7. 메서드 단위 예외 설계 원칙

- 메서드 1개당 throw 가능한 예외는 1~2개로 제한한다.
- 예외는 항상 상위 계층(Service → Controller → Handler)으로 전파한다. catch 후 무시(빈 블록) 는 절대 금지한다.
- 실패 경로는 반드시 로그로 드러내야 한다. 4xx는 WARN, 5xx는 ERROR.
- 비동기 처리(`@Async`, `ApplicationEvent`)에서 발생하는 예외는 `AsyncUncaughtExceptionHandler`를 등록해 ERROR 레벨로 기록한다.
