# 코드 규칙 — 장인몰 (미담)

> 아키텍처는 `서버_아키텍처.md`, API 계약은 `API_공통규칙.md`, 예외 설계는 `예외_설계.md` 참고.
> 이 문서는 **코드를 작성하는 방식** 에 대한 팀 내 합의다.

---

## 1. 계층 구조

```
presentation/   @RestController — HTTP 진입점, 유효성 위임만
application/    @Service — 유스케이스 조합, 트랜잭션 경계
domain/         Entity, Value Object, Domain Service — 비즈니스 규칙
infrastructure/ Repository, 외부 클라이언트 — 기술 세부사항
```

**계층 간 참조 방향**: `presentation → application → domain ← infrastructure`
도메인 간 참조는 **ID만** 허용. 다른 도메인의 Entity 직접 주입 금지.

## 2. 네이밍

| 대상 | 규칙 | 예시 |
|---|---|---|
| 클래스 | PascalCase, 풀네임 | `NotificationService` (NotifSvc ✗) |
| 메서드 | camelCase, 동사+명사 | `findByMemberId`, `markAsRead` |
| 상수 | UPPER_SNAKE_CASE | `MAX_RETRY_COUNT` |
| 패키지 | 소문자, 단수 | `notification.domain` |
| 테스트 메서드 | camelCase 영어 | `markAsRead_notFound` |
| `@DisplayName` | 한글 | `"읽음 처리 — 404 알림 없음"` |

축약 금지. `id`, `url`, `dto`처럼 관용적으로 굳은 것만 예외.

## 3. 클래스 작성 규칙

### 3-1. 메서드

- **18줄 이내** (Javadoc 제외)
- **들여쓰기 1단계** — 중첩 if/for가 2단계 이상이면 메서드 분리
- `else` 사용 금지 — early return으로 대체
- `private` 메서드는 `public` 메서드 **아래**에 모아서 배치

```java
// ✓ early return
public void cancel(Long orderId, Long memberId) {
    Order order = findOrThrow(orderId);
    validateOwner(order, memberId);
    order.cancel();
}

// ✗ else
public void cancel(...) {
    if (order.isCancellable()) {
        ...
    } else {
        throw ...
    }
}
```

### 3-2. 원시값·문자열 포장

비즈니스 의미가 있는 원시값은 Value Object로 포장한다.

```java
// ✓
public record Price(int value) {
    public Price { if (value < 0) throw new BusinessRuleViolationException("가격은 0 이상"); }
}

// ✗ 도메인 메서드 시그니처에 int price 그대로 노출
```

### 3-3. 컬렉션

도메인 내부 컬렉션은 **일급 컬렉션**으로 포장한다.
Controller/Service 반환용 List는 일반 List 허용.

### 3-4. null 금지

비즈니스 코드에서 `null` 반환·체크 금지.

```java
// ✓
return repository.findById(id).orElseThrow(NotFoundException::new);

// ✗
Notification n = repository.findById(id).orElse(null);
if (n == null) throw ...
```

### 3-5. setter 금지

Entity는 의미 있는 도메인 메서드만 노출한다.

```java
// ✓ notification.markAsRead()
// ✗ notification.setStatus(UNREAD)
```

### 3-6. 매직값 금지

숫자·문자열 리터럴은 상수 또는 Enum으로 추출한다.

```java
// ✓
private static final int MAX_RETRY = 3;
// ✗
if (retryCount > 3) ...
```

## 4. 계층별 책임

### 4-1. Presentation (Controller)

- HTTP 매핑, 요청/응답 변환만 담당
- 비즈니스 로직 **금지**
- 유효성 검사는 `@Valid`에 위임 — 직접 검사 금지
- `ResponseEntity` 또는 DTO 반환 (`ApiResponse` 래핑은 `GlobalResponseAdvice`가 처리)

```java
@PostMapping("/products")
public ResponseEntity<ProductResponse> create(@RequestBody @Valid ProductCreateRequest request) {
    return ResponseEntity.status(201).body(productService.create(request));
}
```

### 4-2. Application (Service)

- 유스케이스 단위로 메서드 1개
- 트랜잭션 경계 — 조회는 `@Transactional(readOnly = true)` 메서드 단위 명시
- 권한·존재 검증은 **Service**에서 수행 (`NotFoundException`, `ForbiddenException`)
- 비즈니스 규칙 검증은 **Domain 객체**에 위임

### 4-3. Domain (Entity / Value Object)

- 상태 전이·불변식 검증을 메서드로 캡슐화
- `BusinessRuleViolationException`, `ConflictException` throw 가능
- `ForbiddenException`, `NotFoundException`은 **Service 전용** — Entity에서 사용 금지
- `@Version` 낙관적 락은 동시성 시나리오가 있는 Aggregate Root에만 적용

### 4-4. Infrastructure (Repository / 외부 호출)

- JPA 기본 → 성능 이슈 발생 시 QueryDSL → Native Query 순서
- DB/JPA 예외는 직접 처리하지 않고 `GlobalExceptionHandler`까지 전파
- 특정 UNIQUE 제약 위반을 비즈니스 의미로 바꿔야 할 때만 catch 후 재throw

```java
// 필요한 경우에만
try {
    wishlistRepository.save(wishlist);
} catch (DataIntegrityViolationException ex) {
    throw new ConflictException("이미 찜한 상품입니다");
}
```

## 5. 테스트

### 5-1. 분류 및 파일 역할

| 파일 접미사 | 범위 | 외부 의존 |
|---|---|---|
| `JunitTest` | 단위 — 순수 로직 | 없음 (Mock) |
| `JunitExceptionTest` | 단위 — 예외 경로 | 없음 (Mock) |
| `IntegrationTest` | 통합 — DB 포함 | 실제 DB (Mock 금지) |
| `IntegrationExceptionTest` | 통합 — DB 포함 예외 경로 | 실제 DB |

Controller 슬라이스 테스트(`@WebMvcTest`)는 `RestDocsControllerTest` 상속.

### 5-2. 메서드 명명

```java
@Test
@DisplayName("읽음 처리 — 404 알림 없음")   // 한글 — 리포트 표시용
void markAsRead_notFound() { ... }           // 영어 — 코드 참조용
```

패턴: `[메서드명]_[시나리오]` — `cancel_alreadyCancelled`, `create_duplicateConflict`

### 5-3. GIVEN-WHEN-THEN

```java
// GIVEN
when(notificationService.findOne(anyLong(), anyLong()))
    .thenThrow(new NotFoundException());

// WHEN
ResultActions result = mockMvc.perform(get("/api/notifications/{id}", 999L));

// THEN
result.andExpect(status().isNotFound())
      .andExpect(jsonPath("$.errorCode").value("NOT_FOUND"));
```

### 5-4. 커버리지

- 코드·라인 커버리지 **95% 이상 100% 이하**
- REST API / AsyncAPI 엔드포인트 **100% 문서화 + 테스트**

### 5-5. REST Docs 작성 기준

에러 응답 필드는 `RestDocsControllerTest.ERROR_RESPONSE_FIELDS` 상수 재사용.
성공 응답 `data.*` 필드는 엔드포인트마다 다르므로 **인라인** 선언.

```java
// ✓ 에러 케이스 — 헬퍼 사용
.andDo(documentError("notification-get-one-404", TAG, "알림 단건 조회 - 알림 없음", "..."));

// ✓ 성공 케이스 — data.* 인라인
.responseFields(successEnvelopeFields(
    fieldWithPath("data.id").type(NUMBER).description("알림 ID"),
    ...
))
```

## 6. 관측 (조용한 실패 방어)

기능을 미뤄도 관측은 미루지 않는다. 아래 조건 없이는 구현 미완으로 간주한다.

| 지점 | 요구사항 |
|---|---|
| 비동기 (`@Async`, `ApplicationEvent`) | `AsyncUncaughtExceptionHandler` 등록, ERROR 레벨 기록 |
| Redis Stream PEL / 재시도 | 소진 후 DLQ 이동 경로 코드상 추적 가능 |
| 외부 API 호출 | 타임아웃·실패 경로 테스트 필수 |
| `catch` 블록 | 빈 블록 절대 금지, 반드시 로그 또는 재throw |

로그 레벨 기준: `4xx → WARN`, `5xx → ERROR + stack trace`.
